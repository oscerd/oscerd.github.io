Most weeks I go and find the vulnerabilities. This week they arrived together. Monday 23 November was a coordinated Apache disclosure day, with Jena, Solr, StormCrawler, IoTDB and Pinot all posting at once, and Karaf followed the next morning. So the post almost assembles itself, and the part that stood out to me is that a single day of unrelated projects landed on two or three versions of the same mistake.

The reason I write these down is that a CVE identifier and a severity score tell you how urgently to book a maintenance window and nothing about what actually went wrong. The mechanism is the part worth keeping, because it travels from someone else's code into how you read your own. The longer version of that argument is in [the CVE stigma post](/2026/02/16/the-cve-stigma-we-need-a-new-security-culture.html){:target="_blank"}.

[Last week](/2026/11/18/java-vulnerabilities-of-the-week-12-18-november-2026.html){:target="_blank"} was authentication: credential checks that defaulted to success, and work that ran before the request was authenticated. This week sits one layer over, in authorization and scoping, with a quieter thread of resource-exhaustion bugs underneath. The two I take apart are Apache StormCrawler, where a scoping control was disabled because the code read the wrong setting, and Apache Karaf, where the console's permission list did not cover every way into the console's privileges.

## The week in five

- **Apache StormCrawler, four CVEs, disclosed 23 November, fixed in 4.0.0.** The crawler's `HostURLFilter` is meant to keep a crawl on the hosts or domains you scoped it to. In `CVE-2026-82442` (Low) its `configure` method reads the `ignoreOutsideDomain` setting but tests for the presence of `ignoreOutsideHost` instead, so a config that sets only domain mode is treated as unconfigured and the filter passes every URL. The other three are what an unscoped crawl can then do: `CVE-2026-82446` (Moderate) follows a `robots.txt` redirect to any address the worker can reach, loopback and cloud metadata included, carrying the crawl's `Authorization` header with it; `CVE-2026-82444` (Moderate) sends a host-only session cookie to any host; and `CVE-2026-82445` (Important) lets crawled content inject crawler-control metadata through the unescaped SQL status store. All affect `stormcrawler-core` 3.0.0 before 4.0.0. First deep dive below.

- **Apache Karaf, three CVEs, disclosed 24 November, fixed in 4.4.13 and 4.5.0.** Karaf's SSH console restricts which commands a role may run through a command ACL. `CVE-2026-129959` (Important) is that the SFTP and SCP file-transfer subsystems on the same SSH port are not covered by it, so a user with only the `viewer` and `ssh` roles can read `etc/users.properties` and `etc/host.key` and drop a bundle into `deploy/`. `CVE-2026-130808` (Important) and `CVE-2026-124615` (Moderate) are that `feature:requirement-add` reaches the same provisioning action as the admin-only `feature:install` but has no ACL entry, so that same user can make Karaf start an arbitrary bundle. One advisory prints `4.4.12` as its fixed version, which is inside the affected range; the other two say `4.4.13`, so treat `4.4.13` as the fix. Second deep dive below.

- **Apache Jena and Fuseki, seven CVEs, disclosed 23 November, fixed in 6.3.0.** The two to look at first are both in Fuseki. `CVE-2026-86155` (Critical, CVSS 4.0 10.0) is server-side request forgery through SHACL validation: a SHACL SPARQL target can make the server issue outbound requests, though the advisory does not say which destinations are reachable. `CVE-2026-124324` (Critical) is that a SPARQL `SERVICE` clause can reach administration operations that are supposed to be restricted to localhost. Alongside them `CVE-2026-86156` (Important) is a path traversal where a SPARQL Update request reads graph data outside the intended directory, and four more are denial-of-service in the ARQ query engine (`CVE-2026-97893`, `CVE-2026-103333`, `CVE-2026-120502`, and the `CVE-2026-86154` Turtle parser stack overflow). Everything affects Jena through 6.2.0. The advisories are brief on mechanism, so I am repeating what they state rather then the code path.

- **Apache Solr, two CVEs, disclosed 23 November, fixed in 9.11.0 and 10.1.0.** `CVE-2026-86312` (High, CVSS 3.1 8.8) is that the `/admin/ping` health-check endpoint can trigger more than a health check: under rule-based authorization a client holding only the low-privilege `health` permission can cause actions that should need more, and the sample `security.json` the `bin/solr` CLI installs leaves `/admin/ping` unauthenticated, so in that default an attacker needs no credentials at all. `CVE-2026-53672` (Medium, CVSS 3.1 6.5) is an authorization bypass in Solr's Zookeeper HTTP endpoints: an authenticated account with `zk-read` permission can read `/security.json`, which holds credential hashes and the authorization configuration, without passing the security-read check. The ping bug affects 9.0.0 before 9.11.0 and 10.0.0 before 10.1.0; the Zookeeper bug affects 8.11.1 before 9.11.0 and 10.0.0. The ping finding credits Calif.io working with Anthropic, the people behind last week's [Java4Shell](/2026/11/18/java4shell-openjdk-base64-memory-corruption.html){:target="_blank"}.

- **Apache Pinot, `CVE-2026-134858`, Moderate, disclosed 23 November, fixed in 1.6.0.** Anyone allowed to submit a URI ingestion job can point ingestion at a local file the controller process can read, and if that file parses under the destination table's schema and input format, anyone with query access to the table can then read its contents. The submitter and the reader do not have to be the same party. It affects 0.7.1 through 1.5.1, and the controller flag `controller.ingestFromURI.allowLocalFileSystem` should stay at its default of `false`. The find came through the Zero Day Initiative (ZDI-CAN-28625).

Two honourable mentions, both denial-of-service. Apache IoTDB shipped four heap-exhaustion bugs fixed in 2.0.12 (`CVE-2026-60076` through `CVE-2026-60079`), mostly authenticated clients getting past a row-limit cap on the REST or Grafana paths, with one on the REST `fastLastQuery` cache-hit path that builds its result in memory without a bound; the affected ranges vary by CVE and reach back to 0.13.0 for three of them. And Apache OpenNLP's coordinate name finder carried a regular expression that backtracks catastrophically (`CVE-2026-120404`, Moderate, disclosed 19 November, fixed in 2.5.13 and 3.0.0), so text fed through that finder can drive CPU to a standstill; it affects `opennlp-tools` 2.0.0 before 2.5.13.

## Apache StormCrawler: a control that fails silently

StormCrawler is a toolkit for building web crawlers on Apache Storm. When you point a crawler at the open web you scope it: stay on these hosts, or stay on these domains. That scope is a security boundary as much as a politeness one, because a crawler that wanders can be steered, and one that carries credentials can be steered into handing them over.

`HostURLFilter` is the component that holds the scope. It has two independent modes, `ignoreOutsideHost` to stay on the exact host and `ignoreOutsideDomain` to stay on the registrable domain. In the affected versions, `HostURLFilter.configure` reads the `ignoreOutsideDomain` parameter but, when it decides whether domain mode was configured, tests for the node that belongs to `ignoreOutsideHost`. So if you set only `ignoreOutsideDomain`, the presence check looks at the wrong key, finds nothing, and concludes domain mode was not configured. The domain flag stays false, the filter's guard short-circuits, and every URL passes. Nothing throws and nothing is logged. The mirror case, setting only `ignoreOutsideHost`, throws a `NullPointerException` at startup. Projects generated from the StormCrawler archetypes avoid both, because their shipped filter configurations set both parameters.

Once the crawl is not scoped, `CVE-2026-82446` turns it into server-side request forgery with a credential leak. On a `/robots.txt` fetch, `HttpRobotRulesParser` resolves a redirect's `Location` and re-fetches, for up to five hops, and that loop checks neither scheme nor host nor port (`http.allow.redirects` covers page fetches only). So a crawled site can aim the robots.txt fetch at loopback, a private range, or a cloud metadata endpoint, and every cache miss triggers it. The fetch is blind, since the body is only used to build robots rules. The leak is the sharp part: the okhttp protocol applies its configured headers to every request, including the `Authorization` header built from `http.basicauth.user` and `http.basicauth.password`. okhttp would strip `Authorization` on a host change, but StormCrawler follows the redirect itself, so that stripping never runs and the crawl credentials go to the host the redirect names.

The fix in 4.0.0 checks each scoping parameter on its own, and follows a robots.txt redirect only when the target shares the source's scheme, host and port, with `http.robots.redirect.crosshost.allow` to opt back in. If you cannot move yet, set both scoping parameters explicitly, set `http.filter.ipaddress.exclude` to cover loopback, private, link-local and CGNAT ranges (it runs after DNS resolution, so it also catches the redirect hops), and rotate any crawl credentials that may have left the building.

### Why I find it interesting

This is CWE-670, an always-incorrect control-flow implementation, in its plainest form: a security-relevant setting is read from one key and tested against another. The check is not weak, it is looking at the wrong variable. The important part is the failure mode. The filter does not throw, does not warn, does not degrade in any way you would notice; it stops protecting while the crawl keeps running and looks healthy, which makes the mirror case (the `NullPointerException` on the other key) the kinder outcome, because that one fails loud.

The lesson I take back is about silent controls in general. A control that can be disabled without anything breaking is one whose quiet you cannot read as good news. When you wire a security setting, the question is what happens when it is misread or left unset: if the protected action still proceeds and nothing says so, that is the finding, not an edge case. On the reader's side the fix is a test that asserts the control is actually on, because a crawler that stays on-domain and a crawler whose scoping has silently switched off look identical in the logs until the day one of them follows a redirect to `169.254.169.254`.

## Apache Karaf: authorize the effect, not the command name

Karaf is the OSGi runtime a good deal of Java infrastructure has been assembled on: it is what ServiceMix booted into, what older ActiveMQ and Camel distributions ran on, and what plenty of in-house platforms still sit on. You administer it over SSH console, and you restrict what each role can do with a command ACL, a set of config files such as `etc/org.apache.karaf.command.acl.feature.cfg` that map command patterns to roles. The intent is that a `viewer` can look but not change, and only `admin` can install or start things.

`CVE-2026-129959` is the file-transfer path. The command ACL governs commands typed at the console, which go through the shell interpreter. The Karaf SSH server (MINA SSHD) also exposes the SFTP subsystem and the SCP command factory on the same port, and with `sftpEnabled=true`, the default in `etc/org.apache.karaf.shell.cfg`, those serve the `karaf.base` directory tree. They are not shell commands, so they never pass through the interpreter, so the command ACL never sees them. After the initial `sshRole` login check, nothing else gates them. A user holding only `viewer` and `ssh` can read `etc/users.properties` (the user and password store) and `etc/host.key`, and write a bundle into monitored directories like `deploy/`, which Karaf picks up and runs. That is disclosure of the credentials and arbitrary code execution from role meant to be read-only. The fix adds an `sftpRole` property that defaults to `admin`; the interim mitigation is `sftpEnabled=false` if you do not need file transfer.

`CVE-2026-130808` and `CVE-2026-124615` are the requirement commands. The feature ACL restricts `feature:install`, `feature:uninstall`, `feature:start` and `feature:stop` to `admin`, and has no entry for `feature:requirement-add` or `feature:requirement-remove`. Karaf's command guard, `SecuredSessionFactoryImpl`, lets a command run when no ACL rule matches it, which the advisory calls `NO_MATCH`, so an unlisted command is permitted rather than denied. The catch is that a requirement reaches the same work as the command the ACL does restrict: `RequirementAdd` hands the requirement to `FeatureService.addRequirements()`, and the resolver treats a `bundle:` requirement as a bundle install-and-start and a `feature:` requirement as a feature install. So a `viewer` and `ssh` user runs `feature:requirement-add bundle:<uri>`, and Karaf downloads, installs and starts that bundle with the full privileges of the JVM, the effect that the admin-only `feature:install` existed to prevent. The interim mitigation is two lines in the feature ACL config, `requirement-add = admin` and `requirement-remove = admin`, picked up at runtime without a restart; the fix is 4.4.13 or 4.5.0.

### Why I find it interesting

Both halves are CWE-862, missing authorization, and both come from the same assumption: that naming the sensitive commands in an ACL covers the sensitive actions. It does not, for two reasons the week lays side by side. First, the ACL lives on one interface, the command interpreter, and the SSH server has other interfaces (SFTP, SCP) that reach the same files without going through it, so a permission list written for commands was never going to apply to them. Second, inside the interpreter more than one command reaches the same effect: `feature:requirement-add` provisions a bundle just as `feature:install` does, so an ACL that lists `install` but not `requirement-add` is guarding the name and not the capability. The `NO_MATCH` default is what makes the second one bite, because an unlisted command is allowed, so every route to a privileged effect has to be enumerated or it is open.

The generalisable lesson is in the heading: authorize the effect, not the command name. When you protect an action with an allowlist, the question to run is what are all the ways to cause this effect, and does the control sit where they converge or on each name on its own. If the control is a list of names and the default is allow, then every alias, every sibling command and every other interface that reaches the same action is a gap until it is named. The sturdier place for the check is the action itself, here installing and starting a bundle, rather than each command string that can trigger it.

## What I take away from this week

First, one disclosure day, several projects, two shapes of the same authorization mistake. The controls that broke are not weak checks, they are checks in the wrong place or on the wrong thing. StormCrawler reads the wrong setting and the scope control switches off without a sound. Karaf's ACL guards the command names it knows and not the file-transfer channel or the sibling command that reach the same effect. Solr's ping permission is low-privilege but the endpoint behind it is not, and its Zookeeper endpoint hands the security config to a read role. Jena's `SERVICE` clause reaches admin operations a deployment restricted to localhost. The common review question is worth taking home: for each privileged effect, where does the authorization decision actually sit, and is that the only path to the effect.

Second, the resource-exhaustion thread underneath. IoTDB's four heap-exhaustion bugs, Jena's SPARQL property-path and expression DoS, and OpenNLP's catastrophic regex are one family: an input whose cost is unbounded. Most are authenticated, which lowers the score, but an authenticated DoS is still a DoS when the credential is cheap or shared. If you run a public Jena SPARQL endpoint, the `arq:optPathFlatten=false` workaround is worth setting today, its a one-line change to the execution context.

Third, where the fixes reach people, because almost all of these are direct upgrades rather than transitive BOM bumps: StormCrawler 4.0.0, Karaf 4.4.13 or 4.5.0, Jena and Fuseki 6.3.0, Solr 9.11.0 or 10.1.0, Pinot 1.6.0, IoTDB 2.0.12, OpenNLP 2.5.13 or 3.0.0. Jena is the exception worth calling out, because it is a common RDF toolkit embedded inside larger applications, so that one does travel as a dependency: check your lockfile, not only your servers. And where you cannot upgrade today, several ship a config mitigation you can apply now, Karaf's two ACL lines, Jena's optimiser flag, Pinot's local-filesystem flag and StormCrawler's IP exclude list among them.

Fourth, briefly, AI on the finding side again, stated as the fact it is. Two advisories name it outright: StormCrawler credits the ASF using Claude agents to study open-source projects, and Solr's ping bug credits Calif.io working with Anthropic, who found last week's OpenJDK Base64 bug. Several other finder handles this week carry AI branding (`MopMonk-AI`, `bugbunny.ai`, a Trend ZDI alias), but their advisories do not say any tooling was used, so I am not counting those. That is three weeks running with at least one AI-assisted find in the set, and I am still only noting it.
